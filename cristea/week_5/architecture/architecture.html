Flows

The core of the game is one path: a climb on a phone becomes points in a building and maybe a change of owner. The sequence below follows it hop by hop.

Sign in

467810

The app sends the e-mail to POST /v1/auth/otp. The api checks the university domain and the rate limits in Valkey, stores a salted hash of a 6-digit code and has Azure send it. POST /v1/auth/verify allows 5 attempts and returns an access JWT (15 minutes) and a refresh token (30 days). Each refresh rotates the token; reusing an old one revokes the whole family, which catches a stolen token. Tokens live in the Android Keystore.

Join a team and check in

347

The player picks a faculty team for the season (POST /v1/seasons/{id}/join, one team per season). At a building they scan the signed entrance QR (HMAC and time window checked on the server) or send one location fix (PostGIS, within 30 m of the footprint). The check-in lasts 90 minutes, 24 hours once "pick a building" lands in Week 5. The app then calls setActiveCheckin and the Kotlin service starts the sensors.

A building flips

89511

The flip is published once and every replica's hub forwards it, so it does not matter which replica holds a player's socket. A phone that was offline sends since=<last id> on reconnect and gets the missed events from game_event. A phone with no socket open polls GET /v1/me/events in its 15-minute job. No Firebase or push service is involved; this is our own channel (course rule).

Reads

478

Building standings are one PostgreSQL query. Leaderboards come from Valkey sorted sets and are rebuilt from PostgreSQL when the season's one-hour marker is missing. History and today's figures come from /v1/me/segments and /v1/me/season-stats, with rejection reasons shown.

Phones without a barometer

47

The player scans a sticker on a stair landing (a signed fwl1. token). POST /v1/landing-scans needs a valid check-in and is worth 20 points. The phone keeps a 10-minute cooldown per building.

Deploy

1213

A merged pull request builds an image tagged with the commit. deploy.sh <sha> on the VM decrypts the secrets into memory, pulls that image, migrates, starts the stack and waits for health checks. If they fail within 90 seconds it puts the last good image back.

Now: the pilot

Under one request per second in the background, about 30 open sockets.

Why it copes

  • The phones do the heavy work. A sensing phone reads the barometer 10 to 25 times a second, and the server only ever sees one small summary per climb.
  • Uploads are batched (up to 100 climbs) and sent every 15 minutes, so one player costs a few requests an hour.
  • The api keeps no session state (signed JWTs) and flips travel between replicas through Valkey, so the two replicas are interchangeable from day one.

Weak points

  • One VM is a single point of failure. An Azure capacity outage in Sweden Central on 29 October already kept it down.
  • PostgreSQL, Valkey and two Python processes share 2 vCPU and 4 GiB.
  • No backups, no monitoring (/metrics is a stub), and staging is the same stack as production.
  • Caddy retries a replica that refuses connections but cannot take out one that hangs.

10,000 players: one university

About 11 polls a second, 3,000 open sockets, 1.4 climbs a second at peak, 110 MB of climbs a month.

What breaks first

  1. Memory: the database cache competes with the api processes for 4 GiB.
  2. Database connections: each replica can open 20 (pool 10 plus 10 overflow) and PostgreSQL allows 100 by default, so five replicas would already use them all.
  3. Any restart of the one VM stops the game for everyone.
  4. Jobs still run by hand: next month's partition, purging old rejected uploads and expired codes.

Changes, and why

PostgreSQL on its own VM, with a streaming standbyThe database gets its own memory and a failover target, and survives an app VM going down.
pgBackRest to Azure Blob with WAL archivingPoint-in-time recovery, losing at most 5 minutes of data (plan 7.7).
PgBouncer in transaction modeMany replicas share a few dozen real database connections.
Load balancer and a second app VM, 3 api replicas eachOne VM outage no longer stops the game, and deploys go one VM at a time.
Valkey replica with SentinelRate limits fail closed, so a Valkey restart would answer 503 to every sign-in and upload.
Celery worker and beatPartitions, purges and leaderboard rebuilds run on a schedule, outside user requests.
Monitoring, alerts and a k6 load testMeasured limits replace these estimates, and alerts fire before players notice.
Custom sending domain for Azure e-mail, with a raised quotaSign-in codes must not be throttled when a season starts and everyone signs in at once.

None of this needs a code change in the api: tokens are stateless and the hub already shares flips between any number of replicas.

1,000,000 players: national scale

Up to 1,100 polls a second, 300,000 open sockets, 140 climbs a second at peak, 11 GB of climbs a month (today's 32 GiB disk would be full in about three months).

What breaks first

  1. Socket fan-out. Every flip goes to every socket of the season, so one flip means about 300,000 messages, and ten flips a second means 3 million, all from Python processes that also hold 300,000 sockets.
  2. The claim transaction. Each upload recomputes the building's owner from all of its verified climbs of the last 7 days while holding that building's row lock. Uploads in a popular building queue behind each other, and each one gets slower as the week's climbs pile up.
  3. One PostgreSQL server takes every read and every write, including 1,100 feed polls a second.
  4. The leaderboard rebuild reads the whole season from PostgreSQL every hour.

Changes, and why

Realtime gateway as its own service; sockets subscribe to topics (season, the building on screen, own team)Messages grow with the players who care about a flip, not with all players, and sockets scale apart from REST.
The upload only checks and stores climbs; a queue partitioned by building feeds claim workersNo upload waits on a building's lock. One worker per building applies climbs in order and recomputes once per batch instead of once per climb.
Daily totals per team and building in their own tableThe owner becomes the sum of 7 daily rows, the same cost no matter how many climbs a building gets.
PostgreSQL primary with automatic failover (Patroni), read replicas and PgBouncerWrites stay on the primary; standings, history, the event feed and rebuilds move to replicas.
Cache standings and each season's latest event id in ValkeyMost polls answer "nothing new" without touching PostgreSQL.
Valkey cluster with sharded pub/subOne node can no longer hold every rate-limit key, leaderboard and event.
Autoscaled VM groups across availability zonesCapacity follows the peaks between classes, and a zone outage does not stop the game.
Contract change: the upload no longer returns flipsFlips are decided later by the claim workers and reach the phone over the socket or the feed.

The course rule keeps us self-managed (no managed database or cache, plan 7.2). Outside the course, managed PostgreSQL and a managed cache would take most of this operations work away.

What already scales and stays at every stage

  • Detection on the phone: the server never receives raw sensor data, only one summary per climb.
  • The outbox, the Idempotency-Key and segment_receipt: a retry during an overload never counts a climb twice.
  • Stateless JWT sign-in: any replica can serve any request.
  • Monthly partitions on climb_segment: old months are dropped as a whole partition, not deleted row by row.
  • Pub/sub between replicas: the hub was written for more than one api process from the start.
  • Our own notification channel: no dependency on a third-party push service's limits.

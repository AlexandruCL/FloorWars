FloorWars, the simple version

The whole system in seven boxes and six arrows, small enough to draw on one sheet and explain in two minutes. The detailed sheet has every component and all 13 connections.

The drawing

Explain it by following one climb

  1. 1The player signs in with a code sent by Azure Email 6, picks a faculty team and checks in at a building. The sensor service starts measuring height (barometer) and steps. When height goes up with about 4 to 10 steps per metre, it is stairs; height without steps is an elevator and scores nothing. The climb is saved on the phone and sent later over HTTPS, so it is never lost without internet.
  2. 2Caddy is the front door: it handles HTTPS and passes each request to one of the two API copies. Two copies means one can restart while the other works.
  3. 3The API checks the climb again (a modified app cannot be trusted), saves it in PostgreSQL, adds the points to the player's team, and recomputes who owns the building: the team with the most points in the last 7 days. All of this is one database transaction, so it is saved completely or not at all.
  4. 4If the owner changed, the API tells Valkey. Valkey keeps the leaderboards in memory and passes the news to both API copies.
  5. 5Each API copy pushes the news over the live WebSocket to the phones. The phones of the team that lost show "AC took the Politehnica building". A phone that was offline catches up when it reconnects. We built this channel ourselves because Firebase is not allowed.

GitHub tests every change, builds the server, and a deploy script runs the new version on the VM.

Scaling in three steps

Now, about 100 players. One small VM is enough because the phones do the hard work: the server gets one short summary per climb, not the sensor data. Weak point: if that one VM stops, the game stops.

10,000 players. Put the database on its own server with a standby copy and backups, add a second app server behind a load balancer. The API needs no code change, because its copies already share news through Valkey.

1,000,000 players. Live messages get their own servers, since one flip would go to about 300,000 phones. Climbs go through a queue per building so busy buildings do not wait on each other, and read copies of the database take the load of screens and leaderboards.

Player numbers are estimates from how often the app talks to the server, not measured load.
